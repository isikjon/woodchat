# PROJECT_REQUIREMENTS — Внутренняя система чатов и публикаций Woodstream

## 1. Цель проекта

Компания должна общаться с клиентами и публиковать анонсы через **собственную** систему (backend + веб + мобильные приложения), которая продолжает работать при блокировке Telegram/WhatsApp и без VPN. Внешние платформы (WhatsApp, Telegram, VK, сайт) — только дополнительные каналы дистрибуции контента; их сбой не должен влиять на внутренние чаты.

Источник истины для контента — внутренний Laravel-backend (`chat.woodstream.online`), а не Telegram-канал (текущие пайплайны TG→WA и TG→VK должны стать «внутренняя публикация → все каналы»).

## 2. Роли и матрица разрешений

Роли уже существуют в БД: `users.role` ∈ {`user`, `manager`, `admin`} (+ `is_admin`). Все проверки — на сервере, UI лишь скрывает недоступное.

## 3. Функциональные требования

### ФТ-1. Внутренние чаты (backend уже есть; довести и подключить iOS)
- Личные и групповые чаты, мегагруппа-broadcast; пагинация истории; reply/forward; статусы отправки (отправляется/отправлено/ошибка/повтор); отсутствие дублей (идемпотентность по client_message_id); realtime через Reverb; офлайн-очередь исходящих; восстановление истории после переподключения.

### ФТ-2. Мегагруппа анонсов
- Единственная корневая broadcast-группа. Писать в неё могут только manager/admin (через публикации). Пользователи видят публикации в хронологическом порядке, могут реагировать и комментировать (если разрешено).

### ФТ-3. Публикации
- Сущность `Publication`: текст, вложения (альбом до N фото с порядком), автор, `comments_enabled`, статус: `draft` / `scheduled` / `publishing` / `published` / `partially_published` / `failed` / `cancelled`.
- Отложенная публикация: `scheduled_at` хранится на сервере в UTC (+ исходный часовой пояс), исполняется Laravel scheduler'ом независимо от клиентов; защита от двойного исполнения (блокировка + переходы статусов); перенос и отмена до наступления времени; журнал действий.

### ФТ-4. Единый центр публикаций (мультиканальность)
- Каналы: `internal` (мегагруппа — обязательный), `whatsapp` (существующий Node-сервис `/whatsapp/send-album` — не ломать), `telegram` (Bot API), `vk` (существующая локальная очередь LocalVkPublisher/расширение), `site` (опционально — блог/страница анонсов), `woodstream_app` (читает internal через API — отдельной отправки не требует).
- Статус по каждому каналу: `pending` / `sending` / `published` / `error` / `disabled` / `retry_required`; результат и внешний ID сохраняются; повторная отправка только в выбранный канал; сбой канала не отменяет остальные.
- Бизнес-логика не привязана к SDK каналов — каналы реализуются адаптерами с единым интерфейсом.

### ФТ-5. Комментарии
- Вкл/выкл per-публикация (manager/admin); при выключенных: поле ввода скрыто, backend отклоняет новые комментарии; счётчик комментариев.

### ФТ-6. Реакции
- По принципу Telegram: список реакций под сообщением, счётчики, одна реакция пользователя на сообщение заменяется/снимается, без дублей (уникальный индекс уже есть), realtime-синхронизация, единый набор эмодзи в вебе и приложениях.

### ФТ-7. Статистика публикаций (только реально собираемое)
- Просмотры и уникальные пользователи (событие «публикация показана» от клиентов), количество реакций и комментариев, дата/автор, статусы и ошибки по каналам. Никаких синтетических метрик.

### ФТ-8. Приложение Woodstream (магазин)
- Раздел чатов показывает ленту анонсов из мегагруппы через внутренний API (пагинация, кеширование, альбомы, даты). Источник — backend, не Telegram. Мост аутентификации `mobile-auth` уже существует.

### ФТ-9. Промокоды и подарочные карты
- Backend-модели и транзакционные сервисы уже есть; добавить API для менеджеров (поиск, статус, срок, номинал/остаток, проверка применимости, активация, погашение, история, привязка к клиенту/заказу) c проверкой ролей и журналом.

### ФТ-10. Веб-версия (Vue)
- Экраны публикаций (создание/редактирование/планирование/статусы каналов), комментарии, статистика, промокоды/гифткарты — в рамках прав; остальное уже есть.

### ФТ-11. iOS-приложение
- См. «Открытые вопросы» (§7, В-1) — выбранный путь: собственный клиент к внутреннему API.

### ФТ-12. Локализация
- Русский — основной язык всех UI. iOS: String Catalog/Localizable.strings, плюралы, локализация дат; без хардкода строк. Серверные ошибки → человекочитаемые русские сообщения.

### ФТ-13. Push-уведомления
- Существующие каналы (VAPID web-push, мобильные токены) + новые события: новая публикация, ответ на комментарий, реакция, результат/ошибка публикации для менеджера. Диплинки в конкретный чат/публикацию.

## 4. Нефункциональные требования

- Внутренние чаты работают при недоступности любых внешних API.
- Отправка сообщения — оптимистичная, с локальным статусом и ретраем; отсутствие дублей при повторной отправке.
- Списки сообщений: плавная прокрутка при 10k+ сообщений, превью изображений, кеширование.
- Все критические проверки прав — на сервере; защита от IDOR; rate limiting на отправку сообщений/комментариев; лимиты размера файлов; аудит действий менеджеров.
- Секреты — только в переменных окружения сервера; не в мобильном коде и не в git.
- Миграции обратимы, индексы на выборках чатов/публикаций.

## 5. Пользовательские сценарии (ключевые)

1. Менеджер создаёт публикацию с альбомом из 5 фото, сохраняет черновик, затем планирует на завтра 10:00 (Мск). Ночью сервер перезапускался — публикация всё равно выходит в 10:00: появляется в мегагруппе, уходит в WhatsApp и VK; Telegram недоступен — канал в статусе `error`, менеджер получает push, нажимает «Повторить» только для Telegram.
2. Обычный пользователь открывает приложение — видит анонсы, листает альбом, ставит реакцию, пишет комментарий; менеджер выключает комментарии — поле ввода исчезает, API отклоняет новые комментарии.
3. Пользователь без прав пытается создать группу — сервер возвращает 403.
4. Менеджер в чате ищет подарочную карту по номеру, видит остаток, погашает часть номинала в счёт заказа; повторное погашение той же суммы блокируется транзакцией; операция в истории с именем менеджера.
5. Покупатель с приложением магазина Woodstream (без мессенджера) открывает раздел чатов и видит те же анонсы с фото и датами.

## 6. Критерии приёмки

- Все проверки прав из матрицы (§2) подтверждены серверными тестами (403 для запрещённых действий).
- Публикация исполняется после перезапуска сервера; двойного поста нет (тест на конкурентный запуск воркера).
- Сбой одного канала не влияет на остальные; статусы каналов отображаются в вебе.
- Комментарии при выключенном флаге отклоняются сервером (422/403), поле скрыто в UI.
- Реакции синхронизируются между двумя открытыми клиентами < 2 сек.
- Лента анонсов в приложении Woodstream приходит из внутреннего API (проверка: Telegram отключён — лента работает).
- Промокод нельзя активировать дважды (конкурентный тест на транзакцию).
- В iOS-приложении нет строк на английском в пользовательском UI.
- Release-сборка iOS собирается в архив без ошибок.

## 7. Ограничения и открытые вопросы

- **В-1 (ключевой). Судьба iOS-приложения.** Текущее «приложение» — SDK StreamChatSwiftUI, жёстко привязанный к SaaS GetStream: подключить его к внутреннему Laravel API нельзя. Варианты: (A) написать собственный iOS-клиент к внутреннему API `chat-panel` (полная независимость, большой объём работ, UI-компоненты SDK частично переиспользуемы только как референс); (B) остаться на Stream SaaS (быстро, но платная внешняя зависимость и второй источник данных — противоречит цели). **Принято допущение: вариант A** как единственный совместимый с целью. Требует подтверждения заказчика.
- В-2. Канал «сайт»: что считается публикацией на сайте — пост в блог woodstream.online или отдельная страница анонсов? Допущение: канал реализуется адаптером, по умолчанию `disabled`, включается после уточнения.
- В-3. VK: публикация идёт через chrome-расширение на машине менеджера (полуавтомат). Полный автомат требует VK API-токен сообщества. Допущение: используем существующую локальную очередь.
- В-4. Приложение Woodstream (iOS/Android магазина) отсутствует в доступных репозиториях — есть только PHP-мост. Для него готовится API-контракт и список изменений (см. TECHNICAL_PLAN.md), правки клиента магазина — вне доступного кода.
- В-5. Локальной копии БД `new_woodstre` нет — миграции проверяются синтаксически и на staging; порядок запуска описывается в инструкции.
- В-6. `woodstream_prod-main` и Node-сервис не под git — перед правками инициализируется git для отката.
- В-7. Push в iOS требует APNs-ключей и платного Apple Developer аккаунта — вне доступов текущей сессии.
