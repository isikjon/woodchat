# TECHNICAL_PLAN — порядок реализации

Принцип: сначала модели данных, API, роли и backend-логика; затем веб, приложение магазина и внешние каналы; iOS-клиент — параллельно после стабилизации API. Ничего работающее не переписывается без необходимости; существующая интеграция WhatsApp (Node/Baileys) сохраняется и подключается адаптером.

## Фаза 0. Подготовка (низкий риск)
1. `git init` в `woodstream_prod-main` и Node-сервисе, базовый коммит (точка отката).
2. Убрать отладочную запись `temp_ai.log` из `ChatMessage::booted()` (безопасное исправление производительности).
3. Зафиксировать env-переменные новых модулей (без секретов в коде).

## Фаза 1. Backend: публикации и роли (ядро)
1. Миграции: `publications`, `publication_channel_results`, `publication_views`, `chat_audit_logs` (+ индексы).
2. Модели + `PublicationPolicy` (manager/admin).
3. `PublicationService`: CRUD, планирование (UTC + timezone), переходы статусов, идемпотентная публикация (lock), ретраи.
4. Каналы: интерфейс `ChannelAdapter`; адаптеры `internal` (пост в broadcast), `whatsapp` (HTTP → Node `/whatsapp/send-album`), `telegram` (Bot API), `vk` (существующая очередь), `site` (заглушка disabled).
5. API `/api/chat-panel/publications/*` + просмотры/статистика; серверный запрет комментариев при `comments_enabled=false`; запрет создания групп для роли user.
6. Console-команда `publications:process-due` (everyMinute, withoutOverlapping, runInBackground).
7. Feature-тесты: права (403), планирование, конкурентность, частичный сбой канала.

Зависимости: ничего — стартовая фаза.

## Фаза 2. Backend: промокоды/гифткарты для чат-панели
1. API поверх существующих `PromoCodeService`/`GiftCardService`: поиск, статус, проверка, погашение (DB-транзакции + lockForUpdate), история.
2. Права manager/admin, журнал операций, тест на двойное погашение.

Зависимости: Фаза 0.

## Фаза 3. Веб-версия (Vue)
1. Раздел «Публикации»: список/черновики/календарь, форма с альбомом, планирование, статусы каналов, кнопка повтора по каналу.
2. Мегагруппа: рендер публикаций, комментарии (скрытие поля), реакции realtime, лайтбокс альбомов (vue-easy-lightbox уже есть).
3. Экран статистики; экран промокодов/гифткарт.

Зависимости: Фазы 1–2 (API).

## Фаза 4. Приложение Woodstream (магазин)
1. Публичный (авторизованный) endpoint ленты анонсов с пагинацией и ETag — тот же, что для iOS.
2. API-спецификация + список изменений для клиента магазина (репозиторий клиента недоступен — документ `WOODSTREAM_APP_API.md`).

Зависимости: Фаза 1.

## Фаза 5. iOS-клиент (после подтверждения В-1)
1. Новый app-target (не SDK): сетевой слой (Sanctum), WebSocket Reverb (Pusher-протокол), хранение токена в Keychain.
2. Экраны: список чатов, чат (пагинация, статусы, ретраи, идемпотентность), мегагруппа (альбомы, реакции, комментарии), вход.
3. Кеширование (изображения — можно переиспользовать Nuke-форк из SDK), офлайн-outbox.
4. Локализация ru (String Catalog), push APNs + диплинки.
5. Подготовка App Store (bundle id, privacy, release-архив).

Зависимости: Фазы 1–2; APNs-ключи от заказчика.

## Фаза 6. Финальная стабилизация
1. Прогон чеклиста тестирования (сеть, перезапуски, большие истории).
2. Аудит безопасности (IDOR, rate limiting, секреты).
3. Документация: запуск, миграции, env, TestFlight.

## Порядок запуска миграций (staging → production)
```bash
php artisan migrate --pretend   # проверка плана
php artisan migrate --force
php artisan schedule:list       # убедиться, что publications:process-due зарегистрирована
```
